AI-enabled analytics · Governed self-serve BI

Can a business question get a governed answer?

A certified-metric layer for U.S. commercial electricity data, with a measured evaluation of how often it is right, how often it declines, and how it fails.

Executive summary

Situation Business teams want to ask data questions in plain English, and language models can now produce a fluent answer to almost any question.

Complication A model that writes its own SQL can return a confident number with no agreed definition behind it, and a finance team cannot audit it. Wrong answers are worse than no answer.

Resolution Let the router choose only among certified metrics, compute every number from fixed reviewed SQL, validate each request, and decline everything else. On 115 questions written after the router was frozen, it answered 90.1% of answerable questions correctly and declined 96.3% of out-of-scope ones, with 4 confidently wrong answers (3.5%).

Recommendations

  1. Make the metric dictionary the contract for any self-serve data assistant. The model may route to a metric but never calculates, and every answer carries its definition, source and caveat.
  2. Set acceptance targets before launch and measure on questions written after the router is frozen. Proposed targets: at least 90% answer accuracy, at least 95% correct declines, and a wrong-answer rate under 2%. On point estimates the baseline meets the first two and misses the third.
  3. Close the vocabulary gap with an LLM router behind the same validator, and score it on the same sets before switching. Every confidently wrong answer was a vocabulary or grain error that a rule-based router cannot see.
  4. Show how each question was interpreted and log every miss. Misroutes then become new synonyms or new certified metrics rather than silent errors.

Most misses are safe; the dangerous ones are vocabulary and grain errors

Exhibit 3 · Why the 14 unseen-set failures happened

Source: failures on unseen sets 1 and 2 (70 + 45 questions), each labeled by cause in scripts/build_report.py.

So what: 10 of 14 misses were safe (declined or asked a follow-up). The 4 wrong answers all came from words the router did not know ("pay per kWh", "year-over-year", "drop") or from a ranking over regions it quietly answered with states. That is where an LLM router should help, and where it needs measuring.

How the evaluation was run, and what it does not show

  • Question sets were written by the project author. They are not independent users. The dev set (65) was used to tune; unseen set 1 (70) was written after the router and metrics were hashed (eval/FREEZE.txt); the router was then fixed generically for its failures (v2, eval/FREEZE_v2.txt) and scored once on unseen set 2 (45). Unseen set 1 is no longer clean after those fixes and is not rescored.
  • The pooled figure mixes two router versions (v1 on set 1, v2 on set 2), each on its first run.
  • No LLM was run. The sandbox had no model access, so only the deterministic router is measured. A Gemini router with the same output schema and validator is included and unit-tested against mocked responses, but its accuracy is unknown.
  • Warehouse: SQLite behind a thin adapter (DuckDB was not available here). The data are public EIA series, so the numbers are real but the metric owner and policy targets are illustrative.
  • Small samples: 81 answerable and 27 decline questions in the pooled figure; differences of a few points are not meaningful.
  • An MCP server (askkpi/mcp_server.py) exposes ask_kpi, query_metric, list_metrics and describe_metric to any MCP client; none accept SQL.

Companion project: Electricity Cost-Risk Study. Data: U.S. Energy Information Administration.
